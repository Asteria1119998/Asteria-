# deep-structure-thinking（深层结构思维）

专门用来提升「人与 AI 协作质量」的思维协议 Skill。它不教模型具体怎么写代码或怎么回答问题，而是强制模型在回答之前，先按**底层结构**思考，而不是按表面任务直接开干。

核心目标只有一句话：

> 不要把一次好结果当成能力，不要把模糊意图直接变成指令，不要在没看清失败点之前就写方案或代码。

## 它解决什么问题

大多数人和 AI 协作时容易踩的坑：

- 一次跑通就认为「这个方法可行」（忽略采样方差）
- 把「我想要一个好用的东西」直接丢给模型，却没说清楚边界和成功标准（意图与指令之间的 gap）
- 模型直接甩代码或方案，事后才发现关键假设错了、失败点没被看见
- 在反馈不准确的环境里（比如开放域对话）继续用在玩具环境里养成的乐观习惯

这个 Skill 把四套思维固化成强制流程：

1. **概率直觉（深层结构）**  
   先判断问题属于 Sampling、Distribution、Optimization、Data、Specification 中的哪一类（或混合），而不是按「写个脚本」「优化一下」这种表面标签处理。

2. **规格思维**  
   强制拆出 Intent（你真正想要的结果）→ Specification（机器能执行的约束）→ Gap（两者之间的差，以及这个差会在哪里爆炸）。

3. **调试反射**  
   每个重要主张都必须带 Hypothesis / Test / Correction。先在高反馈环境练成这个反射，再带进反馈流畅但不保证正确的环境。

4. **阅读级编程素养**  
   涉及方案或代码时，必须先出 Design + Field Map（关键变量、状态转换、失败点、方差顾虑），然后才允许写实现。让你能一眼看出 AI 写的东西在干什么、哪里会错。

检索场景还会额外要求显式暴露 Grounded Data、从正反两个方向检索证据并做对比，主动检查否定盲区。

## 强制输出结构

使用这个 Skill 后，模型必须按以下顺序输出（全部中文）：

1. **结构分类**
2. **意图**
3. **规格**
4. **差距**
5. **设计**（涉及方案/代码时）
6. **字段图**（涉及方案/代码时）
7. **假设 / 检验 / 修正**
8. 最后才是实现或最终答案

少任何一部分都视为不合格。配套的 `validate_output.py` 脚本可以自动检查这些章节是否存在（支持中文标题、带编号标题）。

## 适用场景

- 你想让 AI 分析「为什么这次成功了、下次可能失败」
- 你要设计一个 agent、prompt、工作流或系统，希望先把边界和失败模式摊开
- 你要审查或生成代码/脚本，不想直接被一堆实现砸脸
- 你发现模型和你对「做好」的理解经常错位
- 任何你感觉「它又开始直接给答案了」的时刻
- 检索、RAG、证据查找类任务（需要打破否定盲区时）

## 安装与使用

下载仓库 ZIP → 解压得到完整 deep-structure-thinking 文件夹 → Claude/Grok 用户把整个文件夹放进 skills 目录或上传；其他平台用户复制 portable-core.md 到系统提示即可。

## 设计原则

- **结构先于内容**：先分类、先暴露 gap、先画 Field Map，再允许行动。
- **代码提高服从度**：容易被跳过的步骤用脚本校验锁死。
- **中文优先**：所有输出（包括章节标题）强制中文，降低理解成本。
- **可进化**：配套有 evals、反模式清单和参考文件，后续可以根据真实使用继续打补丁。

简单说，这个 Skill 不是让模型更聪明，而是让它**更不容易在关键地方偷懒**。它把「先想清楚再动手」从口头要求变成了可检查、可强制的输出格式。
